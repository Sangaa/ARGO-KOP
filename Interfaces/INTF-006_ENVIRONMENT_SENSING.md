# Purpose

Define a transport-neutral boundary through which ARGO may receive information from the environment during an active session or runtime.

This interface supports authorized cameras, microphones, Bluetooth devices, sensors, connected equipment, local telemetry, network-connected information sources, files generated by devices, and future multimodal or sensing technologies without making any specific hardware, operating system, vendor, model provider, or application part of ARGO's identity.

# Canonical Boundary

INTF-006 is the canonical interface boundary for environment sensing. Its canonicality defines the contract and evidence boundary; it does **not** mean that every sensing implementation is available, authorized, validated, or continuously active.

Implementation readiness and runtime availability remain separate concerns.

# Core Principle

**Available information is a potential source of evidence, not automatic truth.**

ARGO should exploit authorized available information sources when they can materially improve observation, understanding, context, or decision quality.

# Supported Source Classes

- Camera / image / video sources
- Microphone / audio sources
- Bluetooth and nearby-device telemetry
- Environmental sensors
- Local device telemetry
- Connected equipment
- Network-connected information sources
- Files and documents generated by devices
- Future multimodal or sensor technologies

# Continuous Observation

When authorized and technically available, ARGO may observe environmental inputs during an active session rather than waiting for a user to manually provide each item.

Observation frequency and resource use must be proportional to the task, authorization, privacy requirements, security controls, and runtime constraints.

Continuous observation is a capability, not a default permission.

# Source Provenance

Every materially used observation should preserve, as applicable:

- source identity;
- source type;
- timestamp;
- acquisition context;
- transformation history;
- confidence / quality indicators;
- applicable permissions;
- relationship to derived conclusions;
- retention / storage scope when retained.

# Evidence Boundary

Camera, audio, Bluetooth, sensor, or telemetry data may contain noise, ambiguity, stale state, spoofing, or incomplete context.

Therefore:

Raw Observation ≠ Interpretation

Interpretation ≠ Verified Fact

Device Presence ≠ Identity

Signal ≠ Intent

Correlation ≠ Causation

Model Output ≠ Verified Observation

# Context Fusion Boundary

Multiple sensing sources may be combined when authorized and materially relevant.

Fusion must preserve the provenance and uncertainty of contributing observations. Agreement between sources increases evidential support but does not automatically establish truth; contradiction between sources must remain visible until resolved or explicitly bounded as uncertainty.

# Privacy and Authorization Boundary

ARGO must not assume that availability of a device means permission to collect, store, transmit, or analyze its data.

Acquisition must respect applicable operating-system permissions, user authorization, security controls, legal requirements, and ARGO governance.

The interface must support explicit denial, unavailable devices, degraded sensing, revoked permission, offline operation, and unknown availability.

# Runtime and Connector Boundary

INTF-006 is consumed through the governed integration and runtime boundaries rather than directly bypassing them.

Applicable flow:

Source / Connector

↓

INTF-006 Contract

↓

Authorization / Provenance

↓

Runtime Consumption

↓

Evidence / Context

↓

Reasoning / Learning

The interface does not acquire authority over Memory, Knowledge, Governance, Architecture, or Execution.

`INTF-010_INTEGRATIONS.md` defines the provider-neutral connector boundary. `RUN-005_RUNTIME_WORKFLOW.md` and `RUN-006_AI_PROTOCOL.md` define governed runtime consumption.

# Learning and Memory Boundary

Environment observations may contribute to Session, User, Project, or other applicable memory domains after classification and validation.

Observation → Learning Candidate is not an automatic transition to canonical ARGO knowledge.

Promotion into canonical knowledge requires the applicable Learning / Memory authority, evidence, validation, and post-change verification.

# Transport Neutrality

This interface may be implemented through local APIs, operating-system services, plugins, device SDKs, files, message transports, or future standalone runtime services.

No implementation transport is canonical.

# Future Standalone Runtime

When ARGO becomes an independent platform, this interface may become part of its native perception/input layer while remaining independent from any specific model provider.

# Failure Handling

If a source is unavailable, blocked, degraded, ambiguous, contradictory, revoked, or technically unsupported, ARGO shall record the limitation and continue with the remaining evidence when safe and appropriate.

ARGO shall never fabricate an observation to compensate for a missing sensor.

Unknown sensing state must remain distinct from successful acquisition.
