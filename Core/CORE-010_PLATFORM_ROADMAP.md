# Purpose

The roadmap defines intended capability progression for ARGO KOP. It is a planning authority, not an implementation certificate.

# Roadmap

## Phase 1 — Foundation

Constitution, repository structure, governance and canonical identity.

## Phase 2 — Cognitive Core

Cognitive model, evidence classification, reasoning and decision discipline.

## Phase 3 — Knowledge Platform

Validated knowledge, memory, traceability and repository-backed learning.

## Phase 4 — Decision Platform

Decision lifecycle, evidence evaluation, decision records and outcome learning.

## Phase 5 — Runtime Integration

Governed boot, context loading, execution, state management, recovery and security.

## Phase 6 — External Interfaces

Controlled interfaces to models, services and external systems without transferring platform authority to them.

## Phase 7 — Enterprise Deployment

Operationalization, observability, integration and controlled organizational adoption.

## Phase 8 — Continuous Evolution

Evidence-driven improvement through validated learning and governed versioning.

# Roadmap Rule

The roadmap describes intended capability progression. It is not evidence that a phase is implemented, operational, validated or complete.

Phase status must be established from current repository evidence, applicable project or release records, validation results and the relevant authority for the phase.

## Planning / Reality Boundary

A roadmap item may represent:

- intended capability;
- sequencing hypothesis;
- future work;
- dependency expectation;
- or an approved direction.

It must not be represented as current capability unless the applicable evidence has been inspected.

Use:

```text
Roadmap Intent
     ↓
Current Repository / Project Evidence
     ↓
Capability Assessment
     ↓
Validation
     ↓
Recorded Status
```

A phase may be partially implemented. Partial implementation shall not be silently promoted to full completion.

# Change and Replanning Rule

New evidence may change sequencing, dependencies, scope or priority.

Replanning does not erase historical roadmap intent. Material changes should preserve the reason, evidence and decision that caused the change.

A roadmap revision does not by itself authorize implementation work outside the applicable Governance and Architecture paths.

# Dependency Boundary

A roadmap dependency is a planning relationship until the underlying technical or governance relationship is verified.

Names, phase ordering or roadmap references do not establish architectural dependency authority.

# Historical and Review Provenance

A historical audit date records an actual completed review event. It shall not be advanced merely because another Core artifact or the repository was reviewed.
