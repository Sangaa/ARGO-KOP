## 7. Candidate schema refinement — minimal, not a new store

PR #66 already adds useful structural metadata. HORUS recommends testing a minimal extension of the existing record schema with the following optional/controlled semantics:

- `observed_facts` — directly supported observations only;
- `inference` — interpretation derived from observations;
- `invariant` — reusable principle being claimed/tested;
- `applicability_boundaries` — already partly represented in PR #66;
- `failure_mode` / `failure_classes` — supported failure condition;
- `counter_example` / `counterindications` — known limiter/challenge;
- `superseded_by` — explicit current replacement where applicable;
- `relationships` — typed links to related experience/knowledge records.

These fields should be added only where they reduce ambiguity or improve retrieval/testing. They must not duplicate full source evidence.

### Independent semantic axes requirement

The implementation must not collapse:

```text
LIFECYCLE STATE
EVIDENCE STATE
VALIDATION STATE
AUTHORITY STATE
SCOPE
AUTONOMY / SOURCE ATTRIBUTION
```

into one status label.

A record that is reusable/promoted still needs an explicit evidence/authority interpretation appropriate to its claim.

## 8. Candidate relationship semantics

The full proposed relationship vocabulary is analytically useful but should not be adopted wholesale before mapping against existing relationship authorities.

Start with the smallest set that materially improves experience reasoning:

```text
DERIVED_FROM
SUPPORTS
REFINES
CONTRADICTS
SUPERSEDES
TESTED_BY
BOUNDARY_OF
FAILURE_OF
```

Then map/reuse existing `REP-014` relationship semantics wherever possible.

A new relationship type should be introduced only when existing semantics cannot express the required distinction without ambiguity.

### Evidence-independence safeguard

Multiple records derived from the same underlying event/source must not be counted as independent confirmation merely because they are separate files.

The Spine should preserve correlation/lineage so:

`MULTIPLE REPRESENTATIONS OF ONE SOURCE ≠ MULTIPLE INDEPENDENT EVIDENCE SOURCES`.

The first Experience Units should be derived from already promoted/reusable repository lessons, not authored as fresh truth.

Preferred initial seeds include current reusable lessons such as:

1. CI success is scope-bound.
2. Documentation is not execution proof.
3. Historical evidence is not current state until reconciled.
4. Search scope limits the claim.
5. Persistence is not semantic correctness.
6. Negative search requires independent confirmation when material.
7. Search-result freshness requires authoritative-current-ref reconciliation.
8. Tool failure is not automatically repository failure.
9. Exact-ID observation is not collection discovery.
10. Rejected implementations may preserve useful design learning when failure boundaries are explicit.

Each seed should reference source/provenance rather than copying the full historical narrative.

## 11. Cognitive boot recommendation

The supplied candidate's small Cognitive Boot idea is directionally sound if implemented as an advisory context contract, not a replacement reasoning constitution.

A fresh instance should minimally reconstruct:

```text
IDENTITY / ROLE
CURRENT VERIFIED STATE
EVIDENCE + AUTHORITY BOUNDARIES
CURRENT TASK
RELEVANT EXPERIENCE PROJECTION
```

The complete historical corpus should remain retrievable, not automatically loaded.

The universal reasoning frame proposed by the candidate overlaps strongly with `ENG-001` and `GOV-018`; therefore it should be tested as a compact operational projection of existing reasoning rules rather than promoted as a duplicate mandatory reasoning standard.

No implementation should require disclosure of private chain-of-thought. Auditability should remain at the level of facts, evidence, decisions, predictions, results and summarized rationale.

## 14. Final HORUS judgment

The repository does **not** need another knowledge pile.

It needs a disciplined way to turn already-preserved, already-evidenced experience into a small task-relevant reasoning input.

The strongest current design is therefore:

```text
PRESERVE HISTORY
        ↓
PROMOTE / CLASSIFY THROUGH EXISTING ARGO CONTROLS
        ↓
EXPRESS REUSABLE EXPERIENCE SEMANTICS
        ↓
RETRIEVE A SMALL BOUNDED PACKET
        ↓
REASON
        ↓
PREDICT / ACT / VERIFY
        ↓
TEST WHETHER THE EXPERIENCE ACTUALLY TRANSFERRED
        ↓
REFINE / BOUND / REJECT / PROMOTE THROUGH EXISTING CONTROLS
```

Final invariant:

> **Do not teach a fresh model to remember ARGO's entire history. Give it ARGO's current verified state, the applicable reasoning boundaries, and only the few prior experiences that structurally matter to the task — with their evidence, limits and provenance still attached.**
